Every pane of the multiplexer it runs in, ordered by who needs you.

mux-activity finds out where it is from the pane it was started in: REX_SESSION
and REX_BLOCK mean Rex, HERDR_ENV=1 Herdr, LUVUS_ENV=1 Luvus. When several
are set - Herdr started inside a Rex pane inherits Rex's - the nearest
multiplexer above it in the process tree decides: Herdr inside Rex is read
as Herdr. Outside all three it prints why and exits with status 2 before
taking the terminal. --mux rex, herdr or luvus, or the backend setting,
chooses regardless. Only the detected multiplexer's CLI is run.

    mux-activity [--mux rex|herdr|luvus] [-n SECONDS]

Every board has the same shape: a state bar and counts pinned at the top,
AGENTS worst first, then what else is running, then the panes at a prompt.
A program that reports no state is drawn as unknown, never as idle, and a
duration prefixed with ≥ is a lower bound the widget timed itself, because
the state was already in place when it started.

Keys on every board: up/down select and tab jumps to the head of the next
section. ctrl-y and ctrl-e scroll the window a row at a time, as does the
mouse wheel; none of them move the selection. Enter focuses the selected
pane, i shows or hides the idle section, o shows or hides opscope's own
panes (hidden by default), r refreshes now, comma opens settings, q quits.

Press ! to read this widget's notices - warnings that are not about a number on
screen, such as a config file others can read, a recommended tool that is
missing or a Rex server on another API revision - and dismiss them for this
session, for 7 days or for 30. A new notice shows under the footer for a
minute, and a [!] count stays on the top row for as long as it is still true.
Clicking the count opens the same screen.

UNDER REX

Every pane on the server in three sections. AGENTS lists coding agents with
the state they reported themselves - blocked, error, done, working or idle -
with what they are blocked on, their progress and their message. PROCESSES
lists every other pane running something, IDLE the panes at a prompt. Enter
focuses the pane, in whichever session it is - a detached pane, in no
window, cannot be focused. Inside each section the panes are grouped
by session, the session holding the most urgent pane first.

A Rex client, read-only, and every fact on it is labelled with where it came
from. A state is what the program reported with OSC 7501, the Program
Status Protocol; Claude Code reports it on its own. Whether a pane is running
something, and what, is the foreground process Rex names. Durations of
reported states are the server's own timestamps.

    blocked   waiting on a permission, a question or a sign-in, right now
    error     failed and stopped
    done      finished work you have not looked at yet
    attention rang the bell or sent a notification since you last looked
    working   busy
    idle      at rest, waiting for its next instruction
    unknown   an agent is there and has not reported a state

The whole server is read with one `rex do` script on one connection, and
`rex events` wakes a read the moment a status, a process or the layout
changes. It never starts a Rex server, never types into a pane, and never
shows a socket path, an address or a login.

Keys under Rex: j and k select too, and pgup and pgdn scroll a page.
Enter (or f) focuses the selected pane on the server, z zooms it to fill its
window or undoes that, e explains it - every status record, the program's
identity, the last lines its screen shows and why mux-activity read Rex - and esc
or e goes back.

Focus is the server's: Rex makes the window active and the pane focused, and
every app showing that session follows. When no Rex app is attached to the
session, the note says so instead of claiming a screen moved.

UNDER HERDR

Two sections and IDLE. AGENTS lists recognised coding agents with the
lifecycle state Herdr reports, ordered so the ones wanting a human come
first. PROCESSES lists every other pane that is actually running something -
dev servers, monitors, builds - with what it is running and what it costs.
IDLE lists the panes sitting at a shell prompt, by directory, so they can
still be jumped to.

Enter (or f) jumps to whatever is selected: the agent's pane, or the tab
holding that process.

A Herdr client, not a general agent monitor: the inventory and the lifecycle
states come from `herdr agent list`, the workspace labels from
`herdr workspace list`, and the pid behind each pane from
`herdr pane process-info`. Any agent kind Herdr recognises appears here with
no change to mux-activity.

    blocked   waiting on an approval or a question, right now
    done      finished background work you have not looked at yet
    working   busy
    idle      ready for input
    unknown   an agent is present but Herdr cannot classify it

Each row also carries the workspace, how long the agent has held its current
state, and the real CPU and memory of its process.

Keys under Herdr: l toggles workspace labels vs pane ids.

Refresh: pane lifecycle and agent-status events wake a full CLI read.
Workspace label events, socket reconnects, and subscription renewal also
reconcile; CPU and memory sampling remains periodic. Manual r refreshes
immediately, independent of the bounded event socket.

UNDER LUVUS

Five sections are always there, and IDLE is a sixth when idle panes are
shown and present. AGENTS lists the coding agents Luvus recognises with the
lifecycle state it reports, ordered so the ones wanting a human come first.
TASKS and LEASES are the coordination Luvus does and the others have no
equivalent for: claimable units of work, and the file paths an unfinished
task has reserved; the TASKS heading also says whether anything is ready to
claim, because a list with three tasks in it and nothing claimable are
different sentences. RESUMABLE lists agent sessions no pane is holding.
PANES lists every other pane doing something. IDLE, when i has not hidden
it and the session has panes at a prompt, is its own section.

RESUMABLE counts the whole machine, not this session: `luvus agent sessions`
answers for every session on the box, and most of them are usually in
directories no workspace has open. The heading says how many are in a
workspace this session has open, and each row says which it is.

The line under the session says what the focused workspace's checkout looks
like - its branch, how far it is from its upstream, how many entries are
changed, and how many worktrees the repository has. It covers that one
workspace and names it, because `luvus git status` and `luvus worktree list`
take no workspace argument and answer for whichever workspace the session is
focused on. Entries rather than files: git reports a wholly untracked
directory as one entry.

A Luvus client, not a general agent monitor. Every figure comes from the
session's own Universal Harness Protocol 1.0 answers: the pane inventory from
`luvus uhp snapshot`, the agents from `luvus agent list`, the two
coordination sections from `luvus task list` and `luvus lease list`, claimable
work from `luvus task next`, resumable sessions from `luvus agent sessions`,
and the focused checkout from `luvus git status` and `luvus worktree list`.

    blocked   waiting on an approval or a question, right now
    done      finished work you have not looked at yet
    working   busy
    idle      ready for input
    unknown   an agent is present and Luvus classified it as none of those

Each agent also carries how long it has held that state, and how the state was
decided - an integration's report and a reading off screen text are different
strengths of claim and the screen does not flatten them into one word.

Zero tasks and zero leases are the normal state of most sessions and read as
an answer. A source that did not come back says so instead, on its own row.

Keys under Luvus: tab wraps through IDLE when that section is on screen.
Pressing e opens the evidence behind the selected agent's row: how its
identity and its state were decided, how strong each of those claims is,
and - when it is blocked - what luvus says it is waiting for. That last one
is the question a blocked row cannot answer on its own. It also shows what
the pane currently has on screen. The panel is read-only; it never answers
the prompt it is showing you. esc closes it, as does a second e.

Opscope's own panes are matched by local process name and command: a local
ps scan joins the snapshot's root PIDs to their process trees, so run
mux-activity on the same machine as the Luvus session. A failed scan warns that only
Luvus's reported command labels can be filtered.

Refresh: agent status events wake a full read; task, lease, pane, Git and
worktree-only changes are picked up at the configured idle ceiling. Manual
r refreshes immediately, independent of the bounded event wait.
